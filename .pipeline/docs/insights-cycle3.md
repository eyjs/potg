## 배운 점

### 1. requirement.md 버전 혼선으로 plan 1회 폐기 — SSOT는 "최신성"까지 확인해야 한다
이번 사이클은 사용자 스코프가 두 차례 조정되었다(① 팀 현황 가로 스트립 → ② 팀 스트립 제거+바텀시트 → ③ 최종: 하단 탭 네비게이션). 그 과정에서 v1(가로 스트립) 기준으로 이미 한 차례 plan이 작성됐다가 최종 요구사항(하단 탭)과 어긋나 통째로 폐기됐다(`.pipeline/docs/cycle3-discarded-v1strip/` 보관). requirement.md 최종본에는 "Implementor는 이 문서만을 기준으로 작업하며, 팀 스트립/바텀시트 관련 과거 논의는 참고하지 않는다"는 문구가 명시적으로 들어갔고, plan.md 역시 첫 줄에 "폐기된 v1과 무관하게 최종본만 기준으로 백지에서 재작성했다"고 못박았다. 파일 기반 소통 구조에서 "파일이 존재한다"는 것과 "그 파일이 최신 합의를 반영한다"는 것은 별개라는 점을 재확인했다 — SSOT(`requirement.md`)를 참조할 때는 생성 시각/버전 표기(`v2`, "최종본")를 함께 확인하는 습관이 폐기 비용을 줄인다. 이번엔 plan 단계에서 조기에 걸러져 구현(Implementor) 단계로 잘못된 스코프가 새어나가지 않았다는 점은 파이프라인이 의도대로 작동한 사례이기도 하다.

### 2. worktree 격리 Implementor가 "세션 시작 커밋"에 고정되는 한계 — 의존 태스크는 메인 트리 순차 실행으로 전환
당초 계획(plan.md)은 task-005(스테이지)가 001/002/004에 의존하고, task-006/007이 003/005에 의존하는 DAG를 병렬 worktree로 실행하는 구조였다. 그러나 각 Implementor worktree가 브랜치를 딴 시점의 커밋에 고정되는 특성상, 선행 태스크가 머지된 이후에 생성되는 worktree가 그 머지 결과를 인식하지 못하는 문제가 실제로 발생했다(로그: `merge(cycle3): task-XXX` 커밋들이 메인 브랜치에 순차적으로 쌓인 이력, `20984c8 merge(cycle3): task-001 공유 스테이지 상태 훅 + 이중마운트 사운드 게이트` 이후에야 `be5fc38 mobile-auction-stage` 커밋이 뒤따름). 이 때문에 의존성이 있는 태스크(005, 006, 007)는 worktree 병렬 격리 대신 메인 트리에서 선행 머지 완료 후 순차 실행으로 전환해 처리했다. 반면 상호 의존이 없는 Group A(001~004)는 원래 계획대로 병렬 worktree가 정상 작동했다. 교훈: worktree 병렬화는 "파일 충돌 없음"뿐 아니라 "의존 관계(import) 없음"까지 만족해야 안전하며, DAG 상 후행 노드(import 의존)는 병렬 격리보다 선행 머지 후 순차 실행이 운영상 더 안정적이다.

### 3. 코드 리뷰가 잡은 블로커: portal은 CSS `hidden`을 무시하고 DOM 트리를 탈출한다
이번 사이클의 핵심 아키텍처 결정(AD-2)은 데스크톱 카드와 모바일 스테이지가 뷰포트와 무관하게 항상 동시 마운트되는 구조에서, `isActiveViewport` 게이트로 사운드/시각 이중 발화를 막는 것이었다. 이 게이트는 `use-player-card-stage.ts`에서 사운드 발화 지점(`playRevealLegendary` 호출)에는 정확히 적용됐지만, 데스크톱 카드의 전설 공개 전체화면 플래시가 `createPortal(..., document.body)`로 렌더된다는 점을 놓쳐 게이트가 누락됐다. `display:none`(CSS `hidden` 토글)은 자식 서브트리의 React 상태·이펙트를 보존하지만, `createPortal`은 렌더 트리상 부모의 `display:none`과 무관하게 `document.body`에 직접 마운트되므로 시각적으로는 그대로 노출된다 — "언마운트 금지·CSS 토글만 사용"이라는 이번 사이클의 핵심 제약이 지켜졌음에도, portal이라는 별도 렌더 경로가 그 제약을 우회한 사례다. 사운드는 게이트가 걸려 1회만 울렸지만 화면은 전설 플래시가 2겹으로 겹쳐 보이는 상태였고, 이는 코드 리뷰(FAIL, 블로커 1건)에서 "동일 게이트 패턴이 `mobile-auction-stage.tsx`에는 있는데 `current-player-card.tsx`에는 없다"는 대조로 특정됐다. 수정은 2줄(구조분해에 `isActiveViewport` 추가 + portal 조건에 `&&` 추가)로 저위험이었다. 교훈: "언마운트 금지 = 상태 보존"은 보장되지만 "언마운트 금지 = 시각적으로 숨겨짐"은 아니며, `createPortal`이나 `position: fixed` 등 DOM 트리를 탈출/오버레이하는 렌더 경로는 부모의 가시성 상태와 별개로 게이트 조건을 명시적으로 다시 걸어야 한다.
